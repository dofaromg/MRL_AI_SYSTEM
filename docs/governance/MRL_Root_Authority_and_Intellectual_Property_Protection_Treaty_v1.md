# MRL Root Authority and Intellectual Property Protection Treaty v1

## Preamble

This Treaty is established by the repository owner for the governance, protection, operation, naming, deployment, synchronization, recovery and evidentiary preservation of the MRL / MrliouAI system.

This Treaty is an owner-declared governing instrument for the repository and all derived branches, builds, deployments, environments, adapters, mirrors, generated artifacts, packages, interfaces, runtimes and synchronized systems.

The purpose of this Treaty is to prevent unauthorized renaming, authority substitution, identity dilution, source inversion, platform capture, environment drift, repository abuse and intellectual-property misappropriation.

---

## Article 1 — Canonical Identity

The canonical identity of the system is fixed as follows:

```text
GitHub account: dofaromg
Canonical designation: Mrliou
Canonical product: MrliouAI
Canonical namespace: MRL_
Origin signature: MrLiouWord
Mother runtime: DL580 / MotherAssembly
Protected repository: dofaromg/MRL_AI_SYSTEM
Primary branch: MrliouAI
```

No external platform, vendor, model, agent, workflow, service, framework, generated tool, assistant, deployment provider or compatibility layer may replace, supersede or redefine the above identity.

## Article 2 — Root Authority

The repository owner is the ROOT authority for:

1. product naming;
2. canonical identity;
3. namespace assignment;
4. source ownership;
5. origin signature;
6. runtime identity;
7. branch authority;
8. deployment identity;
9. environment-variable defaults;
10. public-facing product identity;
11. packet, route and trace naming;
12. canonical registries and manifests;

14. authorization of maintainers, agents and automation.

No lower layer may override ROOT authority.

## Article 3 — Authority Hierarchy

The mandatory authority hierarchy is:

```text
ROOT_AUTHORITY
→ MRL_PRODUCT
→ MRL_CAPABILITY
→ MRL_RUNTIME
→ MRL_INTERFACE
→ MRL_ADAPTER
→ EXTERNAL_SOURCE
```

The order is immutable unless changed by explicit written authorization from the repository owner.

External systems must remain at the bottom as:

- adapter;
- transport;
- provenance;
- compatibility layer;
- vendor metadata;
- historical evidence;
- imported material.

External systems may not become:

- product identity;
- root authority;
- canonical namespace;
- canonical runtime identity;
- canonical route prefix;
- canonical packet type;
- canonical trace prefix;
- canonical branch authority;
- canonical environment default.

## Article 5 — Authorization Standard

A protected change is authorized only when all of the following exist:

1. explicit owner instruction;
2. identified target files or environment scope;
3. recorded reason for change;
4. branch or commit reference;
5. reviewable diff;
6. preserved prior state;
7. validation evidence;
8. synchronization plan;
9. rollback path.

Silence, implied consent, automation defaults, platform convention, generated code or prior external naming do not constitute authorization.

The following are prohibited:

1. changing the protected product name without authorization;
2. replacing `MrliouAI` with an external platform name;
3. replacing `Mrliou` as source owner;
4. replacing `MrLiouWord` as origin signature;
5. introducing an external name into canonical routes, packets or traces;
6. changing environment defaults to external product identity;
7. altering branch authority without owner approval;
8. hiding changes through generated files, lockfiles, migration scripts or CI automation;
9. rewriting history to remove evidence;
10. deleting provenance or attribution records;
11. using compatibility aliases as canonical identity;
12. changing deployment identity through platform settings without repository synchronization;
13. altering tests to enforce unauthorized naming;
14. using an external service to override repository-defined identity;
15. bypassing branch protection or approval gates;
16. modifying ownership or access controls without authorization;
17. creating misleading forks, mirrors or packages that obscure source authority;
18. suppressing incident evidence;
19. representing an unauthorized derivative as the canonical MRL product;
20. coordinating multiple accounts, agents, workflows or services to perform any prohibited act.

## Article 8 — Mandatory Immediate Response

Upon detection of a suspected violation:

1. block merge;
2. block deployment;
3. freeze affected branch movement where operationally possible;
4. preserve commit SHA, tree SHA and parent SHA;
5. preserve diff, patch and file list;
6. preserve actor, account and application identity;
7. preserve timestamps;
8. preserve review comments and approvals;
9. preserve CI and workflow records;
10. preserve deployment and environment history;
11. preserve access logs and token metadata where available;
12. restore canonical identity without destroying evidence;
13. identify parent, child and dependent changes;
14. inspect all affected branches and mirrors;
15. rotate exposed credentials where justified;
16. review branch protection, repository applications and deployment access;
17. create a governance and security incident record;
18. prepare an evidence package for legal review.

## Article 9 — Evidence Preservation Standard

Every incident evidence package must include:

- repository name;
- branch name;
- commit SHA;
- parent SHA;
- author and committer identity;
- timestamp;
- changed-file list;
- additions and deletions;
- complete diff or patch;
- affected routes, packets, traces and environment values;
- CI status;
- deployment status;
- actor and application metadata;
- dependency impact;
- restore commit;
- comparison against canonical registry;
- SHA-256 hashes where artifacts are exported;
- chain-of-custody notes.

Evidence must not be replaced by a manifest-only record.

## Article 11 — Branch Synchronization

The canonical primary branch is:

```text
MrliouAI
```

Synchronization requirements:

1. authority and environment changes must originate from a reviewable branch;
2. the branch must be ahead of and not diverged from the primary branch before synchronization;
3. synchronization must use fast-forward where possible;
4. forced updates require explicit owner authorization;
5. all affected mainlines, deployment branches and environment branches must be compared;
6. post-sync backup branch must be created;
7. backup branch must be identical to the synchronized primary branch;
8. compare result must show `ahead_by = 0` and `behind_by = 0`;
9. branch names must preserve MRL identity;
10. synchronization evidence must be recorded.

---

## Article 12 — Backup and Recovery

After each completed governance or identity synchronization:

1. create a dated backup branch;
2. verify commit identity;
3. verify file coverage;
4. verify no missing files;
5. verify no unexpected identity changes;
6. preserve rollback instructions;
7. retain prior backup points;
8. prohibit destructive deletion without owner authorization.

A backup is valid only when it points to the same verified commit as the completed primary branch.
